Earlier 2026-09-26 — **Magic-link sign-in (passwordless)**: the login page now offers a second way in — “Email me a sign-in link” flips the form to email-only and a one-time link lands in the inbox. **Needs `prisma db push`** (`User.loginTokenHash` + `loginTokenExpiresAt`); prod applies it by itself, since the Dockerfile's CMD runs `db push` on boot. **Deliberately its own token slot, not `setupToken`:** `setPasswordAction` accepts *any* valid `setupToken`, so sharing the column would quietly let a sign-in link change the password too — a broader power than “sign me in” — and requesting one would also cancel a pending invite. The token is stored **SHA-256 hashed** (`lib/auth/magic-link.ts`), unlike the older `setupToken`: it *is* a live session, so a DB dump or a stray log shouldn't be replayable; lookup stays one indexed equality since the hash is deterministic. **15-minute TTL, single use**, and issuing a new link retires the previous one. **Spent by POST, never GET**: the emailed URL lands on `/login/magic`, which validates the token *without* consuming it and renders a form that submits itself on mount — still one click for a person, but the link previewers and security scanners that GET every URL in an inbox can't burn it first (a visible “Continue to Oprix” button is the no-JS fallback; a ref guards React 19 Strict Mode's double effect). Burning the token is an `updateMany` guarded on the hash still being present, so a double submit or a forwarded link can't mint two sessions. **No enumeration** — always “check your email” whether or not the address exists; the only other response is a rate-limit message, keyed on the *submitted* address either way. Limits are 3/email and 10/IP per 15 min (`lib/auth/rate-limit.ts`, in-process, single host) so the form can't be used to mail-bomb anyone or burn the SMTP quota. Works for invited users who never set a password — holding the inbox is the same proof the invite link asks for. Also extracted the post-login redirect guard to `safeInternalPath()` in `lib/url.ts` (shared with `loginAction`) and tightened it: it now rejects `/\host` as well as `//host`, both of which browsers read as protocol-relative. **Known behaviour:** the proxy bounces an already-signed-in visitor off any public path, so opening a link on a device with a live session lands on that session's home without consuming the token — same as the existing reset flow. Verified: `safeInternalPath` against 17 open-redirect payloads, `hashToken` determinism/shape, the rate limiter's window and per-key isolation, both form modes with the email carried across the switch, the invalid-link page, and — via a throwaway harness (deleted) — that the landing page fires exactly one POST into `consumeMagicLink` with no click. The token round-trip itself is untested locally (Supabase paused) and wants a run on prod. **Hardening after the first prod run:** requesting a link 500'd on prod and replaced the whole sign-in page with Next's error screen — the DB call was unguarded, so a backend fault took **password** login down with it, for an optional feature. Both magic-link actions now catch and return an inline message (matching every other action in the app) with the real error logged server-side; the page, and the password form, survive. `consumeMagicLink` computes its destination inside the try so `redirect()` — which works by throwing — stays outside it. Accepted trade, noted in the code: *while the backend is broken* the message shows only for addresses that exist, a weak enumeration signal that requires the app to already be failing; the alternative is people waiting on a mail that is never coming. The 500 itself was almost certainly the schema: the Dockerfile's boot-time `prisma db push` is non-fatal (`|| echo 'WARN…'`), so if it fails the container serves new code against the old schema and `loginTokenHash` doesn't exist. Quick check without redeploying — request a link for an address that **doesn't exist**: that path skips the write, so if it returns “check your email” while a real address fails, the columns are missing. **Root cause, confirmed on prod:** the column was declared `@unique`, and `prisma db push` treats *adding* a unique constraint to a populated table as possible data loss (“if there are existing duplicate values, this will fail”), so it stops without `--accept-data-loss` — which the Dockerfile omits on purpose. Every boot push had been failing on that one line and starting on the old schema. Fixed by dropping to `@@index([loginTokenHash])`: 32 random bytes never collide, nothing reads the column as a unique key (all four call sites are `findFirst` / `updateMany` / update-by-id), and the change becomes purely additive, so the existing boot push applies it with no flag and no manual step. ## Key conventions / decisions
- **Multi-tenant**: every tenant row carries `companyId`; all queries scope by it; server actions re-check ownership.
- **No UI libraries** — charts, Markdown renderer, combobox, datepicker, modal, WYSIWYG, toast, confirm dialog all hand-rolled. **Profile avatars + the company logo upload to disk** (reserved `Employee.photoKey` / `Company.logoKey`, served via scoped `/api/people/[id]/avatar` + `/api/org/logo`, route URL stored in the existing `avatarUrl`/`logoUrl` so render sites are unchanged; shared `ImageUpload` component). KB article images remain URL-in-markdown. Avatars fall back to **first+last-name initials**.
- **UI feedback**: use `toast` (`@/components/ui/toast`) + `confirmDialog` (`@/components/ui/confirm`) — never native `alert()`/`confirm()`.
- **Times**: company-local wall-clock; 12-hour display; "today" via company timezone (`nowInZone`). **Money**: integer paise.
- **Payroll**: statutory rates live in `lib/payroll/config.ts` (config, not magic numbers); calc is pure; company-level PF/ESI toggles; payslips are immutable frozen snapshots; LOP per-day = Gross ÷ 30.
- **Notifications**: taxonomy/colors/deep-links in `lib/notifications/categories.ts` (isomorphic).
- **Attendance**: the device is the source of raw punches, never of verdicts — Oprix recomputes hours and lateness from the trail (`lib/attendance/punches.ts`, pure/isomorphic) using the employee's `WorkShift.startTime` + `graceMinutes`, keeps the device's own columns verbatim beside them, and flags only the days where the two genuinely contradict each other. A person's days import only once their `Employee.machineCode` is mapped.
- **Task visibility**: per-role scope (`ALL`/`TEAM`/`OWN`) as `task:scope:*` rows in `RolePermission`.
- **Service hierarchy**: `Service.parentId` self-relation — `null` = category (top-level, carries `departmentId`), set = sub-category (inherits the parent's `departmentId`). **Projects link categories** (`ProjectService` → a category); **tasks carry a sub-category** (`Task.serviceId` → a sub-category) which seeds the checklist and scopes assignees to its department. KB articles attach at the sub-category level. Org "General (Tech)/(Design)" categories were created by migration to re-home pre-hierarchy services.
- **Uploads on disk**: `uploads/` at repo root (gitignored); never store bytes in Postgres. Traversal-guarded keys (`lib/uploads.ts`); serving is auth + company-scoped. `Attachment` is polymorphic (`taskId` OR `projectId`); the `AttachmentsPanel` component is shared, parameterized by upload endpoint.

## Workflow caveats (Windows)
- **Adding `@unique` to a populated table breaks the deploy silently.** `prisma db push` counts a new unique constraint as possible data loss and refuses without `--accept-data-loss`, which the Dockerfile's boot push deliberately omits — so it prints `WARN: prisma db push failed` and serves the new code against the **old** schema, giving 500s on exactly the feature you just shipped. Prefer `@@index([col])` unless the uniqueness is load-bearing; if it genuinely is, push it from the Coolify container terminal and check the warning list first.
- Dev server on **port 3000**; restart after **schema changes** (`npm run db:push`) and after **renaming/removing an exported symbol** (Turbopack stale-module error). Stop it before `db:push`/`next build` (it holds the engine DLL + `.next` → EPERM).
- Don't panic at a `prisma:error … ConnectionReset (Os 10054)` **burst right after force-killing `next dev`** — it orphans Supabase session-pooler connections; the next server collides until they're reaped (~a minute). Self-heals; pages still 200. Not a connection-string bug.
- Preview tooling: full-page **screenshots often time out** → verify via accessibility/DOM `eval`; viewport **resets narrow on restart** → `preview_resize` ~1680. A server-action form needs `form.requestSubmit()` to submit programmatically (a synthetic submit-button `.click()` won't).
- React **hydration-mismatch warnings** in dev logs are from the **Bitdefender browser extension** (`bis_skin_checked`), not the app.
- Auto-mode classifier **blocks creating external accounts / sending real emails** and **schema migrations on the shared DB without explicit user OK** — those need confirmation.
